| 规则（按顺序，先命中先生效） | 作用 |

## 2026-10-11：不带资料名的自然问法（尚未部署）

分支 `fix/private-natural-retrieval`，基于 `2bb85d1`。只改私有适配层和策略文件，`mr_index.py`、`mr_corpus.py` 未动；OneDrive 里的 `app` 还是旧代码。此前的评测题都带明确资料名，这一轮针对日常问法：不写文件名，中文问英文资料或反过来。

| 改动 | 解决的问题 |
|---|---|
| 私有分词（`mr_private_index.py`）：去掉英文词首尾的 `.` `:` `/` `-`，重音字母和全角字符归一；复合词保留整体，零件另算且不计入段落长度；`128,500.00` 额外给出 `128500` | `salary:`、`2024.txt`、`1997-06-25.` 这类标签、句尾值和文件名最后一个词搜不到；`Montréal` 被拆成两截 |
| 查询里复合词的零件必须在同一段落里同时出现才计分；含单字符零件的复合词（`2029-1-5`、`4.62`）只按整体匹配 | 部分编号（`88231-40117`）能找到完整编号；查一个不存在的编号或日期时，不会返回所有共用某个年份或前缀的段落 |
| 自动范围总是同时查个人资料，结果与路由到的范围交替合并；段落数超过 `auto_scope_chunk_limit`（默认 20 万）且尚未加载的范围不自动打开 | 「offer 里的期权」「简历里的项目」被关键词路由到股票或代码范围后完全查不到个人资料；一个路由词触发上百秒的分区加载 |
| 长文件内选证据段：关键词与本地向量按名次融合，并带上最佳段落的相邻段，按原文顺序给出。只用检索时已经加载的向量，读证据本身不建索引、不加载模型 | 中文问英文长文件时文件内没有词面匹配，只能返回第一段 |
| 向量段落文本前加「上级目录 / 文件名」，`ENCODER_VERSION` 升到 2 | 年份、资料类型常常只出现在文件名里，向量腿分不清同一类资料的不同年份 |
| 两条腿都找到、融合分数相同的两个文件按问题向量的相似度排序；只被关键词找到的文件仍排在同名次、只被向量找到的文件之前 | 名次 `[0,1]` 与 `[1,0]` 得分相同，此前由插入顺序决定 |
| 索引缓存文件名带代号：`corpus.lexical2.<范围>.enc`、`corpus.semantic2.<范围>.enc`；旧代码的缓存文件原样保留 | 新旧代码共用一个资料库时互相覆盖关键词缓存、互相判对方的向量缓存失效，回退也要重建 |
| 成对评测里基线没有真正用上向量时，不再报告为 hybrid 提升（`baseline_hybrid_actually_used`）；后台验证的分区探针改用私有分词 | 基线悄悄退回关键词仍被算作提升；以 `- - -` 开头的文档让分区探针查不到任何结果、验证反复失败 |
| 中英关键词表从 13 个词扩到 98 组，双向；`of`、`date`、`number` 这类泛词不作为扩展词 | 中文问句在英文资料里没有任何关键词可匹配 |
| 策略规则支持「任意层目录名」（可限定在某个目录之下，支持通配）；默认策略排除 `股票分析` 下的 `originals`、`sources`、`*-sources`、`inputs` 和各处的 `px_cache` | 股票范围绝大部分是可重新下载的原始公告和行情缓存 |

### 这些数字不能说明什么

- 题目和文档都是虚构的，由写这批改动的同一个 agent 编写，关键词表与题目用的是同一类日常词汇。它们说明改动对这些失败形态有效，不代表真实资料上的准确率，也不是独立的人类提问。
- 两份新题集上 hybrid 排第一的比例都低于 BM25（开发集 0.854 对 0.931，留出集 0.702 对 0.853）：多语言小模型在一批格式相近的表单上区分度不够。两条腿的权重需要在新的题集上另行评测，本次没有调。
- 拒答没有改善。hybrid 下所有负例修改前后都返回候选；BM25 下不存在的编号仍然不返回结果，但没有答案的话题性问题会因为关键词表多返回几条相关候选。候选一律是「待核实」。
- 自动范围的合并是固定交替：路由到的范围占 3 条、个人资料占 2 条，没有相关度门槛。一个确实属于代码或股票范围的问题会让出两个位置给个人资料；这个取舍没有用真实问题量过。
- 耗时来自几十到几百份文档的小语料，不能外推到真实资料库。未缓存的范围建关键词索引比原来慢约 1.4 倍（私有分词更细）。

### 部署前后要做的事

1. 在资料源电脑上拉取分支，先跑单元检查和 `verify_private_semantic.py`。
2. 新代码用自己的缓存文件（`corpus.lexical2.*.enc`、`corpus.semantic2.*.enc`），不读也不改旧代码的 `corpus.lexical.*.enc`、`corpus.semantic.*.enc`。关键词缓存首次查询自动建；向量要用新代码按范围 prepare 一次，个人范围此前实测约 25 分钟，在这之前界面会提示退回关键词检索。
3. prepare 完再用已有的加密题集做回归：`mr_private_benchmark.py --labels … --baseline-code <旧代码目录>`。两边各用各的向量缓存，汇总里 `baseline_hybrid_actually_used` 和 `comparison.hybrid_actually_used` 都应为 true，否则不是 hybrid 对 hybrid。原文探针和已用过的自然改写题不应丢失文件或证据。这些题带资料名，只能当回归；新的提升结论需要用户自己写的、不带资料名的新题。
4. 部署时除了 `app` 目录，收集器 `tools` 目录里的 `mr_private_policy.py` 和 `private-policy.json` 也要一起换，两处不一致会让收集和检索用不同的排除规则。确认不回退之后，旧的两类缓存文件可以删掉。
5. 策略哈希变了，下一次导入会重写全部分区；股票分区会明显变小。按路径对真实目录清单估算（不读文件内容），进入股票范围的文件从约 4.1 万个降到约 0.8 万个，自己写的分析和案例库保留。旧分区仍按原有规则在 24 小时后的下一次导入时清理。
6. 股票范围缩小后如果仍超过 20 万段，自动范围不会打开它，界面会提示手动选择；阈值可在 `retrieval-settings.json` 里用 `auto_scope_chunk_limit` 调整。

没有处理的：后台维护循环的开销、分区存储格式、首次查询耗时、OneNote 与带密码 PDF 的收录。

## 2026-10-03：改动及作用

| 改动 | 解决的问题 |
|---|---|
| 私有版加入本地 BM25 + 多语言 E5，复用工作版分词和文件融合 | 关键词表达与原文措辞不同；中英文改写；不向外部 embedding 服务发送私人正文 |
| 资料、倒排与向量缓存加密保存 | 保持个人资料在本机加密存储，避免明文索引进入公开仓库 |
| 个人、项目技术、历史、股票范围隔离，支持手动选择 | 默认个人搜索漏掉项目资料；混合不同来源影响统计和召回 |
| 返回可继续读取的完整来源 evidence | 预览找到文件但遗漏所需事实 |
| 明确资料名先定位文件，再进行文件内 BM25/向量检索 | 正确文件被全库候选截断；资料名干扰问句排序；长文件尾部证据遗漏 |
| 加密成对评测，冻结标签、代码和来源指纹，首次查询前消耗留出集 | 旧结果被重复当作新测试；修改标签掩盖退步；只看总命中而漏掉逐题回退 |
| 部署清单、SHA-256、备份与 Markdown 入口 | GitHub 代码和 OneDrive app 不一致，其他 agent 无法确认运行版本 |

这次没有训练模型。工作学习版共享基础函数保持原有行为；加密存储、独立索引和本地模型由可选私有适配层负责。

## 结论的适用范围和待办

目前证据支持的是“真实来源、明确资料名上下文下的自然改写检索提升”。问句由 agent 写作，同一来源的中英文问题相关；正文哈希分组不能证明完全独立的现实事件。尚未验证无资料名的日常个人记忆问法、独立人类提问、最终回答准确率或拒答质量。

下一轮先检查 6 个证据缺口，再收集新的无资料名日常问题并冻结评测。OneNote 页面、原始密码 PDF 和未准备的其他范围向量仍需各自补齐。不能用检索分数把历史文件当成当前事实。
