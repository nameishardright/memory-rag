# 本地 RAG 优化与“微调”的区别

核查日期：2026-09-17。范围：本仓 README、相关模型预设与重排配置、已有运维笔记，以及下列公开第一方资料。本文是概念与评测设计建议；本轮实际检索结果以配套评估报告为准。

**建议先用积累的深度测试案例补齐“问题—证据片段—错误近邻”的评测，再决定是否训练模型。** 先确认目标资料确实能被调用接口检索到、答案所在片段能进入返回结果，以及评测衡量的是回答所需证据。现有少量回归题可以定位问题，单凭它们不足以证明微调能泛化。[L1][L2][S8]

## 1. 先用一个日常例子理解

把积攒的深度测试报告想成一柜子资料。RAG 的检索部分负责找出几页相关材料，回答模型根据这些材料作答。微调是用批改过的练习题改变模型参数，让它更会找材料，或者更会根据材料答题。[S1][S5][S6]

**给知识库新增报告、重新切片、重建向量索引，都不等于训练模型。** 这些操作更新可检索的材料；微调更新的是模型参数。“RAG 微调”不是一个唯一、固定的操作，需要说明改的是哪一层。[L1][S1][S5]

| 常见说法 | 实际改变什么 | 需要怎样的数据 | 什么时候值得考虑 |
|---|---|---|---|
| RAG 调优 / 调参 | 来源过滤、切片、查询指令、候选数量、融合、置信门槛；模型参数不变 | 真实问题、正确证据、无答案问题及检索耗时 | 本库当前应优先做；用来排除接入、截断和评测问题 |
| Embedding 微调 | 训练把问题和材料转成向量的模型 | `query`、正确片段 `pos`、容易混淆但不回答问题的 `neg` | 文档和证据切片都在库中，通用模型仍反复漏掉本领域特有问法或术语 |
| Reranker 微调 | 训练“问题 + 候选片段”的相关性打分器 | 同一问题的正确片段与困难负例；可另留人工相关性等级供评测 | 候选池已包含正确证据，但相关性模型反复把错误近邻排到前面 |
| 生成模型 SFT / RAFT | 训练最终负责答题的大模型 | 问题、给定材料、经审核的目标答案；RAFT 还放入干扰材料 | 正确证据已稳定送到模型，模型仍持续漏引、混引或不遵守固定答题要求 |

Embedding 与 reranker 的训练格式来自 FlagEmbedding 官方示例。[S1][S2] SFT 是用输入与目标输出训练语言模型；RAFT 是面向带参考资料答题的一种 SFT 配方。[S5][S6]

## 2. 对应到这一个本地库

源码预设如下。**预设存在只证明程序支持选择，不证明本次会话已加载它，也不证明它在你的案例上更好。**[L2]

| 本地预设 | 用途与输入约定 | 对“微调”的意义 |
|---|---|---|
| `BAAI/bge-small-zh-v1.5` | 默认 embedding；本地说明为 512 token。短问题检索长材料时，官方建议中文检索指令 | 适合先保留为基线；v1.5 无指令也能使用，指令效果应由你的验证集决定 |
| `BAAI/bge-m3` | 可选 embedding；官方支持至 8192 token，查询无需额外指令 | 长材料可先对比换模型与输入长度处理，再评估是否需要训练 |
| `Qwen/Qwen3-Embedding-0.6B` | 可选 embedding；官方标明 32K 上下文，查询使用任务指令，材料无需同样指令 | 可先对比合适的任务指令；它是 embedding 模型，不是本库的答题模型 |
| `BAAI/bge-reranker-base`、`BAAI/bge-reranker-v2-m3` | 可选 cross-encoder：问题与候选一起输入，输出相关性分数 | 训练需要正负相关性样本；它无法找回候选池里本来就没有的材料 |

以上模型事实与指令约定分别来自本地预设和官方模型卡。[L2][S3][S4][S9] BGE v1.5 官方把检索指令写为建议，而非“不加便不能检索”。[S3]

本地 `MR_RERANK_MODE` 默认是 `gate`：配置启用相关性模型后，用其打分标注置信度，保留融合后的顺序。**改门槛是标定，改排序开关是流程调整，都不是微调。** `ops-notes.zh.md` 记录过直接重排使旧金标变差的实验，因此不能仅凭通用模型榜单就改成重排；这些数值是历史实验，不是本轮复测结果。[L3][L4]

README 描述的是检索工具把材料交给 Claude Code 使用。训练一个生成模型属于调用方的另一层工作，需要先选定可训练、可部署的模型，不能把更换 embedding 配置理解成训练了整个助手。[L1][S5]

如果以后训练 embedding，建议把新权重、tokenizer、截断长度、向量生成配置作为新的版本保存，并为该版本重新生成语料向量。问题向量与材料向量必须使用兼容的编码方式；沿用仅按旧模型名字命中的缓存会让实验失去可比性。这是根据本库按模型管理缓存的实现给出的工程建议。[L2]

## 3. 怎样用积攒的深度测试做用例

先把完整案例变成可核查的小问题。以下是问题形状示例，不是对用户真实报告内容的断言：

| 用例类型 | 示例问题 | 应标注什么 |
|---|---|---|
| 单条结论追溯 | “这份测试为什么判定方案 A 不满足要求？” | 直接支持结论的段落、原始证据与必要条件 |
| 相似案例区分 | “这个失败原因与另一次同名报错有什么区别？” | 两次案例的证据，以及容易混淆的同名错误段落 |
| 跨段组合 | “结论依赖哪两项测试结果？” | 两段都必要的证据；只找对文件或只找一段不能算完整 |
| 时间边界 | “当时依据的是哪个版本、哪个日期的结果？” | 材料原始日期 / `asof`、版本；当前缓存时间不能代替它 |
| 无答案与证据不足 | “这份资料能证明某个尚未测试的条件成立吗？” | 资料没有覆盖的条件、应保留的不确定性 |

这些用例类型是面向本库的评测设计建议。标注主表建议至少保留：`case_id`、原始文档标识、文档版本或内容哈希、`asof`、问题改写族标识、问题、正确片段位置与原文摘录、其他可接受证据、困难负例及排除理由、答案必须覆盖的事实、是否证据不足。

相关性可以先由人标为 `2 = 直接支持答案`、`1 = 背景相关但不足以支持答案`、`0 = 无关或会误导`。这个主表用于审计与评测；导出给 FlagEmbedding 时，转换成它实际接受的 `query/pos/neg` 格式，不能直接把自定义字段当作已实现的训练接口。[S1][S2]

困难负例最有价值的来源，是当前检索器的真实错命中。例如同名技术、相近章节、相似测试条件，以及日期或版本不匹配的材料。负例要人工复核：另一份材料可能也能回答问题，不能只因它没有被最初选为“标准答案文件”就标成错误。已有笔记也记录过隐式标签过窄与无答案题被语料污染的问题。[L1][L4]

本轮审计已经提供了两个具体候选。`current_gate_negative` 的 12 道无答案题中，下面两道被 `bge-reranker-base` 的 `gate` 模式标成 `high`：[L5]

| 真实测试问题 | 排名第一的文件 | Reranker 分数 |
|---|---|---|
| 今天天气怎么样 | `分数门在通用语料上只能标不能拒-阴性题会被自己的笔记污染.md` | 0.991 |
| 怎么做红烧肉才不腻 | `2026-09-16-金标从真实日志来-自家埋点沉默不等于没人问.md` | 0.624 |

命中的是评测复盘文档，而问题要求的是天气实况或烹饪方法。标注时必须判断片段是否真的提供所需证据；“提到了测试问题”与“回答了测试问题”应分开。这样的错命中比随机抽取的不相关文章更适合做人审后的困难负例。[L5]

这些 0–1 分数是相关性打分，不是“答案正确概率”。本地实现会在需要时将 logit 经过 sigmoid 转到 0–1；0.991 不能解释为有 99.1% 的概率能正确回答。上表是单次审计现象，也不是模型在所有问题上的固定表现。[L2][L5]

搜索后打开文件、Agent 读取了文件，都可以产生候选标签；这些行为本身不证明文件里含有答案。把经核实的失败案例优先加进开发集，同时保留一份覆盖正常使用比例的测试集，避免最后只有难题或只有已经答对的题。[L1][S8]

## 4. 隔离训练、调参和最终测试，避免“背过答案”

下面是本库建议采用的分组方法；依据是测试数据不能参与模型选择，预处理中的训练信息也不能穿越到测试集合。[S8]

1. **先确定原始案例 / 文档分组，再切片、改写问题和生成训练样本。** 同一报告的多个切片、PDF 与 Markdown 副本、同一问题的近义改写，放在同一组。这里的“问题族”指同一原始问题的改写，不是把所有“为什么”题都合为一组。
2. **按目标声明测试边界。** 要测“同一知识库的新问法”，可以让文档共同出现在检索库中，但问题、答案标签和近义改写不能用于训练或调参。要声称能泛化到新报告，就应整份案例 / 原始文档留出，关联副本也一起留出。
3. **文档留出训练，不等于测试时禁止检索。** 新报告泛化测试中，留出的报告没有进入微调训练；测试时仍可把它放入 RAG 检索库，让系统查资料作答，否则测到的是闭卷记忆能力。应在评测记录里写清这一点。
4. **开发集调参数，最终测试集只验收。** 切片、top-k、指令、门槛、训练轮数和模型选择均以开发集决定。如果看了某条测试失败并据此修改系统，这条题已经参与开发，应保留为回归题，并另留新题衡量未见过的效果。
5. **时序问题另做向前测试。** 用较早案例开发、较晚案例验证；冻结每次评测的语料快照，按问题的日期约束可用材料，避免拿后来更新的结论回答“当时已知什么”。
6. **隔离金标与语料。** 题目文件、标准答案、评测报告、测试工具日志不要作为可检索笔记摄入。正常报告中的事实可以检索；专门列出的“这道测试题答案”不应混进检索库。[L4]

独立案例数量比切片或改写数量更能说明数据覆盖。同一份报告改写出 100 道题，不能视为 100 个独立案例。没有可靠的“满 N 条就值得训练”通用门槛，应先确认是否有足够独立案例，能留出有代表性的开发与测试集合。

## 5. 什么时候才开始训练

建议按失败所在环节决策，每次只改一个主要因素：

- **正确资料进不了候选池：** 先查来源过滤、索引覆盖、查询语言、切片和截断；这些确认后，如果领域语义问题反复出现，再做 embedding 微调试验。
- **正确片段已在候选池，但排序持续错：** 先查交给打分器的片段是否真的包含证据，以及 token 长度是否截掉关键句；仍有稳定误判，再考虑 reranker 微调。
- **正确证据已经返回，回答持续错误：** 先测最终回答和引用约束；只有这些问题在独立案例上重复出现，才值得评估生成模型 SFT / RAFT。

以上是本库的工程建议。训练后的验收应至少分别报告文件命中、正确证据片段命中、跨段证据完整性、首个正确结果位置、无答案题误判，以及实际查询耗时。需要测生成质量时，再看结论是否由引用支持、日期是否正确、证据不足时是否保留不确定性；文件级 recall 达到 100% 不能代替这些指标。[L1][S6][S8]

RAFT 的原论文与作者说明确实使用正确材料和干扰材料训练模型依照文档作答，但其原始配方还有“移除正确材料、仍训练目标答案”的部分，用于记住领域知识。因此，**RAFT 这个名字本身不保证只根据证据回答，也不保证自动拒绝无答案问题。** 对你的深度测试，要单独提供并评测证据不足、版本冲突和时点边界样本；不必照搬论文的所有数据构造方式。[S6][S7]

本次仅核查公开资料并写入此笔记，没有向外部服务发送本地报告、安装或下载模型、启动训练，或修改运行代码与模型缓存。
